# Future work and excluded features

Snapshot: 2026-08-23. This file is a release-status ledger, not a promise that
an unavailable product feature can be exercised through a hidden or placeholder
path. Native HNS value and Shakedex source paths are enabled; their complete
persistence, restart, negative-test, integration, and qualification evidence
remains a separate release deliverable.

| Feature | Status | Release boundary |
| --- | --- | --- |
| Handshake ordinary wallet and known-name support | implemented source, release-gated | The authenticated loopback node RPC adapter, bounded restart-safe coin/name-role scans, restoration, history/reorg reconciliation, exact fee-policy integration, ordinary transaction signing, wallet-owned direct HNS/Shakedex composition, and wallet-owned P2PKH TRANSFER/direct-FINALIZE workflows are implemented and the exact source gates passed. Canonical current/proof NameState, exact owner inclusion, versioned action context, typed reservations, single-use approval, and durable action reconciliation remain unavailable to products until cross-process node/wallet regtest, restart/reorg/mempool/adversarial and resource qualification, trusted provider/UI integration, independent review, and reviewed gate changes are complete. |
| Handshake Provider API | implemented source, product unavailable | The checked-in existing-database subprocess remains the five-control locked dispatcher. The exact-account and synchronized-read library compositions expose account, balance, history, receive-target, and known-name reads. Results come from one bounded live HNS reconciliation under an internal exact chain/mempool binding with no backend I/O inside store closures. Public output retains its 128-item bound. Names consent has a separate maximum-64 prompt bound under the unchanged 16 KiB frame: one prompt-time sync displays exact sorted canonical name/hash pairs, pending state freezes that account and set, approval re-syncs and rejects any change, and only the displayed hashes persist. Required approval-schema-v3 `hnsNames` must be negotiated and adopted by browser/mobile consumers before availability. Provider value/module paths remain unimplemented, while the native HNS value source gates are enabled. The synchronized provider regressions are included in the exact CI evidence tracked in `docs/QUALIFICATION.md`; product construction, trusted UI/transport, installed E2E, review, and release evidence remain required. |
| Fixed-price Shakedex | implemented source, unavailable | Exact hash/network/time/locking-coin verification, typed two-phase cancellation, canonical Denuo envelopes, encrypted replay/tombstone-safe board state, protected seller-key allocation, runtime-owned current lock/TRANSFER authority, and runtime-bound negative cancellation admission now exist in source. Cancellation admission binds exact signed target/content to the persisted listing plus selected-account network/trusted time and full account/board fences without requiring a live lock or making a node call; exact persisted retries remain revision-stable after restart/expiry. Durable buyer-fulfillment, seller-recovery, and seller-script-FINALIZE aggregates also exist. The FINALIZE child binds one exact signed parent plus stable canonical TRANSFER/owner/NameState/renewal identity and historical snapshot/mempool evidence, uses a purpose-separated transfer-only funding/signing boundary, and shares the protected reservations, revision-bound approval, final-byte fee evidence, persist-before-broadcast reconciliation, and evidence-backed terminal release. Harmless live binding advances are allowed only when stable identity is unchanged; the HNS runtime still requires exact bindings within each immediate live fence. Current regression evidence is tracked against exact commits in `docs/QUALIFICATION.md`. Product coin selection/startup orchestration, live relay/provider/trusted-UI integration, and regtest/restart/reorg product qualification remain unavailable; the HNS and Shakedex source gates are enabled. |
| HNS/BTC native settlement | implemented source, unavailable | HNS and Bitcoin HTLC/evidence primitives, the HNS node evidence adapter, and a bounded Kyoto supervisor/pre-broadcast journal exist. The pinned Kyoto header/filter/peer persistence gap, Bitcoin signed-spend supervision, published HNS 0.2 settlement profile, end-to-end regtest/restart/reorg evidence, record archival, and resource qualification remain unavailable. |
| HNS/ETH native settlement | contained source, unavailable | Separated offline account derivation, typed dormant transaction/evidence primitives, and deterministic contract source exist. Synchronization, history, send, signing, authoritative evidence, and settlement are hard-disabled behind immutable false gates; embedded Helios proof production/persistence, approved deployment, local-chain qualification, and audit are unavailable. |
| Direct HNS/BTC offer board | implemented core, unavailable | The wallet persists signed, exact, indivisible HNS/BTC offers, cancellations, takes, proposals, and accepted sessions under its own network binding. It has no oracle, reporter/source policy, price history, external API, matching engine, or price authority. Current live offers may be grouped by exact BTC-per-HNS ratio only for display; selection and settlement remain bound to one original offer. Direct peer transport/UI, wallet-controlled HNS and Bitcoin HTLC fund/redeem/refund execution, recovery/reorg evidence, and product qualification remain required. |
| Litecoin module | deferred | A future module must implement `ChainModule`, `UtxoChainModule`, and `AtomicSettlement` and pass the full pair qualification suite. |
| Additional UTXO chains | deferred | No assumption is made that Bitcoin script, sighash, address, fee, dust, or locktime policy is reusable. |
| Additional account-based chains | deferred | Each chain requires a single selected verification model and a narrowly scoped settlement adapter. |
| Additional trading pairs | deferred | A pair is not advertised merely because two wallet modules exist; its complete success/refund/restart/reorg sequence must qualify first. |
| Content aliases | deferred | No alias resolver, provider adapter, or browser path exists. |
| Free generated or donated names | deferred | Free-name grants, three-word acquisition, name inventories, vaults, and sponsorship are excluded. |
| Renewal automation | deferred | Current renewal height may be metadata; alerts, scheduling, construction, automation, toggles, and public-renew scripts are excluded. |
| Domain-service functionality | deferred | Hosted accounts, provider adapters, billing, fiat payments, service accounts, and pooled operations are excluded. |
| Advanced identity | deferred | Only typed Handshake identity-signing boundaries are planned; generalized identity, key export, and name-key signing are unavailable. |
| Handshake auctions and registration | deferred | Ordinary-user OPEN, BID, REVEAL, REGISTER, automatic auction, resource editing, and update flows are excluded. |
| Generic Ethereum applications | unavailable | `window.ethereum`, WalletConnect, arbitrary calldata/contracts, deployment, tokens, NFTs, DeFi, staking, lending, custom RPC, and chain switching are deliberately forbidden. |
| Generic Bitcoin signing/applications | unavailable | PSBT export/signing, raw-transaction signing, alternate production backends, and unrelated Bitcoin script applications are deliberately forbidden. |
| Custodial or wrapped settlement | unavailable | Wrapped assets, custodial exchange accounts, pooled liquidity, AMMs, centralized order books, and server-held wallet keys are prohibited. |

No product-unavailable row may be exposed through a hidden or placeholder value
path. Moving a source boundary to qualified requires corresponding evidence in
`docs/QUALIFICATION.md`; moving it to available additionally requires complete
product integration and a reviewed
release policy.
